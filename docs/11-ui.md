# User interface

## Maturity

Reversible placeholders, deterministic rule actions, failure-open states, interaction-effort budgets and accessibility requirements are Accepted for v0.1. AI-assisted drafts, similarity actions, native-feedback queues, statistics and synchronization UI remain Proposed or Experimental according to their capability contracts.

UI contracts for a Proposed capability are conditional. They become release requirements only after that capability's spec is Accepted and the capability is enabled.

## Principles

- Start useful: deterministic local behavior works before setup.
- Keep the platform usable while ContentLens is pending, degraded or unavailable.
- Complete common, unambiguous actions in one interaction.
- Prefer immediate undo for local reversible actions.
- Ask only for information that changes the result.
- Explain decisions and failures in plain language.
- Keep the current task in context instead of sending the user through unrelated settings.
- Disclose inferred scope before a draft becomes a durable rule.
- Keep advanced profile, model and diagnostic controls in the side panel.

## Interaction hierarchy

Each surface has three levels:

1. One primary action for the current state.
2. Up to two frequent secondary actions.
3. A full menu for advanced or less frequent actions.

The primary action follows the current state:

| State | Primary action | Secondary actions |
| --- | --- | --- |
| Visible item | Hide for now | Show less for now, More |
| Hidden item | Show | Always allow, More |
| Reduced item | Show normally | Hide, More |
| Rule just created | Undo | Review rule, Dismiss |
| Operation failed | Retry or recover | Details, Dismiss |

The "More" menu can contain identity, correction and rule actions. A control does not appear when the adapter lacks the required stable identity or capability. If hiding it would make the state confusing, it remains disabled with a short explanation.

## Content-card integration

Every supported item exposes the smallest useful action set. The expanded menu can contain:

```text
Show this item
Hide for now
Show less for now
Show less of this type
Hide similar content
Always allow this source
Block this source
Prioritize this source
Correct this decision
```

The labels adapt to the platform, such as channel, author or feed.

Known item, source, platform and surface data are carried into the next step. The user does not reselect them. "Hide for now" and "Show less for now" affect only the current item for the current session. "Show less of this type" always opens an editable durable draft. If another action has one safe interpretation, it applies immediately and offers undo. If scope or effect is ambiguous, ContentLens creates an editable draft in place.

## Hidden placeholder

```text
Content hidden

Reason: blocked source
Rule: "Block Example Channel on YouTube Home"

[Show] [Always allow] [More]
```

The placeholder preserves enough layout to avoid a jumping feed. A user can expand the original item for the current session without deleting the rule.

Model-backed decisions use calibrated, user-safe evidence:

```text
Content reduced

Likely match: professional football
Confidence: high
Exception check: no allowed context found

[Show normally] [Correct] [More]
```

A percentage is shown only when calibration evidence supports that precision. Hidden model reasoning, raw prompts and false-precision scores never appear.

## Reduced content

Reduced items remain discoverable through lower opacity, collapsed detail or movement into a "lower relevance" section, depending on adapter capabilities. Accessibility must not depend on color alone.

## Promoted content

Promotion uses a restrained marker and optional sorting within ContentLens-owned views. The extension should not create a misleading native endorsement.

## Side panel

### Overview

- Active platforms.
- Items hidden, reduced and promoted.
- Recent corrections.
- Capability and health status.
- Quick pause per platform.
- Resume the last unfinished draft or recovery action.

### Rules

- Blocked channels and authors.
- Allowed and prioritized sources.
- Exact terms.
- Semantic topics.
- Archetype preferences.
- Search, filters, enable toggle and scope.

### Review queue

- Low-confidence decisions.
- False-positive candidates.
- Optional native platform feedback.
- Sync conflicts only when experimental sync is enabled.

### History

A bounded local history shows decision, reason and correction state. The user can clear it without deleting rules.

### Statistics

- Observed reveal and correction rates, labeled as partial user feedback rather than evaluation-set error rates.
- Most active rules.
- Content reduced by platform and archetype.
- Time saved estimate with disclosed assumptions.
- Useful content discovered through promotion.

### Settings

- Platform adapters and surfaces.
- Decision thresholds.
- Local models and resource limits.
- Cloud inference consent.
- Retention.
- Import and export.
- Experimental synchronization only after its capability is enabled.
- Privacy and data deletion.

## Rule editor

A deterministic identity or exact-term rule uses a compact editor with inferred scope. A semantic rule draft can contain:

- Natural-language description.
- Positive examples.
- Exclusions.
- Effect: promote, allow, reduce or hide.
- An advanced threshold control when the capability exposes a calibrated value.
- Platform and surface scope.
- Test area showing how saved examples would be classified.

An AI assistant may convert the current item and a short instruction such as "show less transfer gossip, but keep technical analysis" into this draft. The draft labels inferred fields, explains missing evidence and remains fully editable. The model never saves, broadens scope or submits a platform action.

## First run

The first run is local-only and has no mandatory questionnaire:

1. ContentLens identifies the current supported platform and offers to enable it.
2. The user can try one reversible item or source action, or open a preview with example data.
3. The result shows the active scope and offers undo.

The panel may offer optional preference setup after the first successful action. Model downloads, cloud providers and synchronization never block or appear as required onboarding.

Starter settings are editable suggestions with examples and exclusions. ContentLens does not silently apply a political, religious or cultural policy.

## Assisted actions

Assistance reduces work only when it can preserve control:

- Suggest a draft after repeated consistent corrections.
- Infer current platform, surface, source and item from context.
- Generate examples and exclusions from a user's instruction.
- Explain which part of a rule matched.
- Offer a narrower scope when a rule would affect many items.
- Group repeated failures or similar corrections into one reviewable proposal.

Suggestions name their evidence, can be dismissed and have a cooldown. Suppression is keyed by proposal fingerprint and evidence version. Repeated dismissal suppresses that proposal until its evidence version changes or the user explicitly re-enables it.

## Batch actions

A batch begins from a user-selected collection or an explicit review queue. Before apply, it shows:

- Number of affected items and sources.
- Platform and surface scope.
- Local changes and external platform actions as separate groups.
- Items that cannot be changed and why.
- The undo or recovery behavior.

Local reversible changes may apply as one confirmed batch. Native platform actions require their own reviewed confirmation and report partial success per item.

## Feedback and operation states

Every user-initiated operation first exposes a transient state while work is unfinished:

| State | UI contract |
| --- | --- |
| Pending | Acknowledge immediately, keep the platform responsive and allow cancellation when meaningful |

It then reaches one terminal state:

| State | UI contract |
| --- | --- |
| Success | Confirm the outcome near its source and offer undo when reversible |
| Partial success | Preserve successful work, identify failures and retry only failed work |
| Cancelled | Stop pending work, retain editable input and identify any effect committed before cancellation |
| Unavailable | Explain the missing capability and show the deterministic or manual fallback |
| Failed | Preserve input, state what did not complete and offer one primary recovery action |

Offline is an environmental condition rather than an operation result. Local work continues, and only the network-dependent part remains pending or reaches `unavailable` with its local fallback.

Messages are deduplicated by operation and cause. Background retries are bounded and never produce repeated toasts. Technical details are available in diagnostics, while the main message stays actionable.

## Perceived performance

- Direct manipulation acknowledges within 100 ms on the reference fixture.
- A spinner is avoided for work that completes within the acknowledgement budget.
- Longer local work shows bounded progress or a clear indeterminate state.
- Model download shows size, progress, pause, cancel and storage impact.
- Feed scrolling and native controls remain responsive during extension work.
- A late result never moves focus, opens a panel or mutates a recycled card.

## Journey budgets

| Journey | Budget |
| --- | --- |
| First useful action | At most three decisions, no account |
| Hide or show one item for the current session | One action |
| Show less of one type | Open draft, review and save |
| Block or allow a known source | One action plus undo |
| Reveal a hidden item | One action |
| Undo the last local rule action | One action |
| Create a semantic rule from an item | One instruction, draft review and save |
| Retry a recoverable failure | One action without re-entering prior input |
| Pause ContentLens on the current platform | One action from the panel |

## Accessibility

- Keyboard access for every card action.
- Screen-reader explanation of current decision.
- Focus restoration after reveal or hide.
- Reduced-motion support.
- Contrast-compliant states.
- Text labels in addition to score color.
- Status changes use a non-disruptive live region and do not steal focus.
- Progressive disclosure preserves a predictable tab order and an accessible path to every action.
